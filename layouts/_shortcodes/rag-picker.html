A reasonable starting point
SQL over your tables (Text-to-SQL)

When answers live in tables, an LLM can translate the question into a SQL query and the system runs it, instead of embedding rows into vectors. Use a read-only database user, validate the generated query, and expose only the tables the user may see.

Then measure: how often the generated query is correct, on a set of real questions with known answers.

A reasonable starting point
Graph retrieval

If a curated source of the relationships already exists (for example, a drug-interaction database), query it directly first. Building a knowledge graph from documents with an LLM can work too, but extraction errors become retrieval errors.

Then measure: entity resolution (are "metformin" and "Glucophage" the same node?) and extraction accuracy on a sample of documents.

A reasonable starting point
A router first, an agent if needed

Try a fixed workflow with a few predefined paths (for example: documents, SQL, or both) and a router that picks one. Move to a free-form agent only if the questions really need open-ended, multi-step tool use.

Then measure: tool-choice accuracy, latency and cost per question. Give any agent step and time budgets, and treat retrieved text as data, not instructions.
